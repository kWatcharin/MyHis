# กฎการเขียน Rust (my-his)

เอกสารนี้คือมาตรฐานการเขียนโค้ดของโปรเจกต์ ใช้กับทุกไฟล์ใน `backend/`
ถ้าข้อไหนขัดกับความจำเป็นจริงหน้างาน ให้เขียนคอมเมนต์อธิบายเหตุผลไว้ตรงนั้น แล้วค่อยแหกกฎ
โค้ดอ้างเลขข้อของเอกสารนี้อยู่หลายที่ (เช่น "ข้อ 11") **ห้ามเลื่อนเลขข้อ** หัวข้อใหม่ให้ต่อท้าย

## 1. หลักการรวม

1. **ให้ compiler จับข้อผิดพลาดแทนคน** ถ้าเลือกได้ระหว่างกฎที่ต้องจำกับการออกแบบชนิดข้อมูลที่ทำผิดแล้วคอมไพล์ไม่ผ่าน ให้เลือกอย่างหลังเสมอ
2. **ชัดเจนดีกว่าสั้น** โค้ดที่อ่านแล้วเข้าใจใน 30 วินาทีมีค่ามากกว่าโค้ดที่ฉลาด
3. **อย่าสร้างนามธรรมก่อนมีผู้ใช้สองราย** trait, generic และ macro ให้เพิ่มเมื่อมีของจริงสองแบบที่ต้องรองรับ ไม่ใช่เพราะเผื่ออนาคต

## 2. ห้าม panic ในเส้นทางปกติ

- ห้าม `unwrap()` และ `expect()` ในโค้ดที่ทำงานตอนรับ request
- อนุญาตเฉพาะ 3 กรณี และ `expect()` ต้องมีข้อความบอกสาเหตุ
  - `main.rs` ตอนเริ่มระบบ เพราะถ้า config ผิดควรล้มทันที
  - ในเทส
  - invariant ที่พิสูจน์ได้ว่าล้มไม่ได้ ข้อความต้องบอกว่า *ทำไม* จึงล้มไม่ได้ ไม่ใช่บอกว่าอะไรล้ม
    ตัวอย่าง `"HMAC accepts keys of any length"` (`crypto.rs`), `"connection semaphore is never closed"` (`conn_guard.rs`)
- ห้าม `unsafe` ทั้งโปรเจกต์
- ห้าม index array หรือ slice ตรง ๆ ถ้าไม่มั่นใจขอบเขต ใช้ `.get()` แทน
- `panic!` ที่หลุดใน handler = 500 และผู้ใช้ไม่ได้อะไรกลับไปเลย ให้แปลงเป็น `AppError` เสมอ

## 3. Error

- แต่ละโมดูลนิยาม error ของตัวเองด้วย `thiserror` ใน `service.rs` และ `repository.rs` (เช่น `disease/service.rs`) ให้บอกความหมายเชิงธุรกิจ ไม่ใช่ชื่อ error ของไลบรารี
- `AppError` (`error.rs`) เป็นตัวกลางตัวเดียวที่ implement `IntoResponse` และเป็นที่เดียวที่แปลง error ของโมดูลเป็นรหัสสถานะ
- ใช้ `anyhow` ได้เฉพาะใน `main.rs` และสคริปต์ ห้ามใช้เป็นชนิด error ของ service หรือ repository เพราะจะทำให้ handler แยกแยะกรณีไม่ได้ (ตอนนี้ยังไม่มีใครใช้ ให้คงไว้แบบนั้น)
- ใช้ `?` แทนการ `match` ซ้อนหลายชั้น
- ห้ามกลืน error เงียบ ๆ ถ้าตั้งใจข้ามจริง ให้ `let _ = ...;` พร้อมคอมเมนต์เหตุผล
- ข้อความที่ส่งกลับผู้ใช้กับข้อความใน log เป็นคนละอย่าง รายละเอียดทางเทคนิคอยู่ใน log เท่านั้น
- **error ต้องไม่บอกใบ้ข้อมูลที่ผู้โจมตีอยากรู้** เช่น login ด้วยรหัสผิดกับ login ด้วยผู้ใช้ที่ไม่มีอยู่ต้องได้ response
  และเวลาตอบเท่ากัน (ฝั่งไม่มีผู้ใช้ verify กับ `dummy_password_hash` ที่สร้างใน `main.rs`) ถ้าจะเพิ่ม endpoint ที่ตอบว่า
  "มี/ไม่มี" ให้คิดเรื่องนี้ก่อนเสมอ

## 4. ออกแบบด้วยชนิดข้อมูล

- ใช้ newtype แทนชนิดพื้นฐานสำหรับ id เช่น `UserId(Uuid)` เพื่อไม่ให้สลับ id ของคนละตารางกันได้
- ใช้ enum แทนการส่ง string ไปมา เช่น `Role` และ `Permission` ห้ามเทียบด้วย `role == "admin"`
- แปลงข้อมูลที่ไม่น่าเชื่อถือให้เป็นชนิดที่ถูกต้องตั้งแต่ขอบระบบ (parse, don't validate) หลังจากนั้นโค้ดชั้นในไม่ต้องตรวจซ้ำ
  - รูปแบบ/ความยาวของฟิลด์ใน DTO ขาเข้าให้ตรวจด้วย `validator` (`#[derive(Validate)]`) ที่ handler
  - แล้วแปลงเป็นชนิดโดเมน เช่น `domain/username.rs`
- ถ้าสถานะหนึ่งเรื่องมี bool หลายตัวที่ต้องสอดคล้องกัน ให้เปลี่ยนเป็น enum
- `Option` ต้องมีความหมายชัดเจน ถ้า `None` แปลว่า "ไม่พบ" ให้ repository คืน `Option` และให้ service เป็นคนตัดสินว่ามันเป็น error หรือไม่

## 5. Ownership และการ clone

- พารามิเตอร์รับ `&str`, `&[T]`, `&T` ถ้าฟังก์ชันแค่อ่าน คืนค่าเป็น owned
- `clone()` ไม่ใช่สิ่งต้องห้าม ถ้ามันทำให้โค้ดง่ายขึ้นและข้อมูลเล็ก ให้ clone ไปเลย ดีกว่าดัน lifetime จนโค้ดอ่านไม่ออก
- แต่ห้าม clone ข้อมูลก้อนใหญ่ในลูป และห้าม `to_string()` เพียงเพื่อให้คอมไพล์ผ่าน
- `PgPool` โคลนได้ราคาถูกโดยออกแบบ ส่ง clone เข้า handler ได้ตามปกติ ไม่ต้องห่อ `Arc` เพิ่ม
- `AppState` ควรเป็น `Clone` ที่ภายในเป็น `Arc` สำหรับข้อมูลใหญ่

## 6. Async

- **ห้ามงานที่บล็อกอยู่ใน async fn** ได้แก่ argon2, การอ่านเขียนไฟล์แบบ sync, `std::thread::sleep` ให้ใช้ `tokio::task::spawn_blocking` หรือเวอร์ชัน async
- งาน CPU หนักที่ผู้ใช้ภายนอกสั่งได้ (argon2) ต้องจำกัดจำนวนพร้อมกันด้วย `Semaphore` ไม่งั้นโดนยิงรัว ๆ แล้ว blocking pool เต็ม (`password.rs`)
- ห้ามถือ `std::sync::Mutex` คร่อม `.await` ถ้าจำเป็นต้องถือข้าม await ให้ใช้ `tokio::sync::Mutex` แต่ก่อนอื่นให้คิดว่าจะเลี่ยงการใช้ lock ได้ไหม
- งานหลายอย่างที่ไม่ขึ้นต่อกันให้ใช้ `tokio::try_join!` แทนการ `.await` เรียงกัน
- ทุกการเรียกออกนอกกระบวนการต้องมี timeout ทั้ง HTTP ขาออก (`turnstile.rs` ตั้ง `VERIFY_TIMEOUT` ให้สั้นกว่า timeout
  ของทั้ง request) และ request ขาเข้า (`TimeoutLayer`/`RequestBodyTimeoutLayer` ใน `app.rs`)
- อย่าสร้าง task ด้วย `tokio::spawn` แล้วทิ้ง ถ้าต้องมีงานเบื้องหลัง ให้เก็บ handle ไว้และปิดให้เรียบร้อยตอน shutdown
- จำไว้ว่า handler ถูกยกเลิกกลางทางได้เมื่อ client ตัด connection หรือชน timeout ถ้างานไหนครึ่ง ๆ กลาง ๆ ไม่ได้ (เช่น รันแล้ว
  ต้องบันทึก audit) ให้ `tokio::spawn` งานนั้นแล้ว `.await` handle ไว้ งานจะได้จบแม้ handler หายไป (`sql_console/service.rs`)

## 7. โมดูลและการเปิดเผย

- `lib.rs` เปิดทุกโมดูลเป็น `pub mod` เพราะ `backend/tests/` เป็นคนละ crate ฟังก์ชันที่เทสระดับ API ต้องเรียกจึงใช้ `pub` ได้
  ส่วนของภายในจริง ๆ ที่เทสไม่ต้องแตะ ให้ใช้ `pub(crate)` หรือ private
- `mod.rs` ของแต่ละฟีเจอร์เป็นหน้าร้าน ระบุชัดว่าเปิดอะไรออกไป (เช่น `pub(crate) use routes::router;` ใน `sql_console/mod.rs`)
- ห้าม `use foo::*;` ยกเว้น prelude ที่ออกแบบมาเพื่อการนั้น และ `use super::*;` ใน `mod tests`
- ไฟล์ที่โค้ด (ไม่นับ `mod tests` ท้ายไฟล์) ยาวเกินประมาณ 300 บรรทัด เป็นสัญญาณว่าควรแยก ไม่ใช่กฎตายตัว แต่ให้หยุดคิดทุกครั้งที่เกิน
  วิธีแยกคือเปลี่ยนไฟล์เป็นโฟลเดอร์ตามหัวเรื่อง เช่น `users/service/` และ `users/repository/`

## 8. การตั้งชื่อ

ตาม Rust API Guidelines

- `snake_case` สำหรับฟังก์ชันและตัวแปร, `CamelCase` สำหรับชนิด, `SCREAMING_SNAKE_CASE` สำหรับค่าคงที่
- ไม่ใส่คำนำหน้า `get_` ใช้ `user.name()` ไม่ใช่ `user.get_name()`
- `as_` คือการยืมแบบไม่เสียค่าใช้จ่าย, `to_` คือการคัดลอก, `into_` คือการยึดครองค่าเดิม
- ชื่อฟังก์ชันบอกสิ่งที่ทำ ไม่ใช่วิธีที่ทำ `lock_account()` ดีกว่า `update_user_column()`
- หลีกเลี่ยงตัวย่อที่ไม่ใช่คำที่ใช้กันทั่วไป

## 9. Derive และ trait

- ใส่ `#[derive(Debug)]` กับทุก struct และ enum เป็นค่าเริ่มต้น **ยกเว้น** ชนิดที่มีความลับ
- ชนิดที่ถือรหัสผ่าน, token หรือข้อความที่ผู้ใช้พิมพ์และอาจมีข้อมูลผู้ป่วย ให้เขียน `Debug` เองให้พิมพ์ฟิลด์นั้นเป็น `[redacted]`
  กันข้อมูลหลุดผ่าน log
  - รวมถึง **DTO ขาเข้า** ด้วย ไม่ใช่แค่ struct ของตาราง
  - ตัวอย่าง: `LookupRequest` (`registration/dto.rs`), `QueryRequest` (`sql_console/dto.rs`), `SqlConsole` (`sql_console/setup.rs`)
  - ใส่เทสที่ `format!("{x:?}")` แล้วตรวจว่าไม่มีค่าลับหลุดออกมา
- `Clone` ใส่เมื่อมีคนต้องใช้จริง ไม่ใส่ไว้ล่วงหน้า
- implement `From` สำหรับการแปลง error และการแปลงชนิดที่ไม่มีทางล้มเหลว ใช้ `TryFrom` เมื่อมีโอกาสล้มเหลว
- อย่าเขียน trait ของตัวเองสำหรับ repository จนกว่าจะมี implementation ที่สองจริง ๆ เทสระดับ API กับ `#[sqlx::test]` ครอบคลุมพอแล้วในตอนนี้

## 10. Iterator

- ใช้ iterator chain แทนลูปสะสมค่าด้วยมือ เมื่อมันอ่านง่ายกว่า
- ถ้าแต่ละรอบอาจล้มเหลว ใช้ `collect::<Result<Vec<_>, _>>()` แทนการ push ทีละตัวใน `for`
- ถ้า chain ยาวจนอ่านไม่รู้เรื่อง กลับไปใช้ `for` ธรรมดาได้ ความอ่านง่ายสำคัญกว่าความเป็น idiomatic

## 11. SQLx

- ใช้ `query!`, `query_as!` และ `query_scalar!` เพื่อให้ตรวจ query ตอนคอมไพล์
  - ข้อยกเว้นอยู่ในโมดูล `sql_console/` เท่านั้น
    - SQL ที่ผู้ใช้พิมพ์ในหน้า SQL (`repository.rs`) ต้องใช้ `sqlx::query(sql)` แบบ runtime
    - DDL ตั้ง role/grant (`setup.rs`) ใช้ `sqlx::query_scalar` แบบ runtime ได้ แต่ชื่อต้องผ่าน
      `format('%I'/'%L')` ฝั่ง Postgres จาก binding ไม่ใช่ `format!` ของ Rust
- สั่ง `cargo sqlx prepare` ทุกครั้งที่แก้ query แล้ว commit `.sqlx/` ไปพร้อมโค้ดและ migration ใน commit เดียวกัน
  แต่ละ commit ต้อง build แบบ offline (`SQLX_OFFLINE=true`) ได้ด้วยตัวเอง
- **ห้ามประกอบ SQL ด้วย `format!`** พารามิเตอร์ต้องผูกผ่าน binding เสมอ
- งานที่ต้องแก้หลายตารางให้ทำใน transaction เดียว เช่น รีเซ็ตรหัสผ่านแล้วลบ session ทั้งหมด หรือแก้ข้อมูลแล้วเขียน `audit_log`
- ระวัง N+1 ถ้าพบว่าต้อง query ในลูป ให้เปลี่ยนเป็น query เดียวที่ join หรือใช้ `= any($1)`
- ตั้งขนาด pool และ timeout อย่างชัดเจน อย่าใช้ค่าเริ่มต้นโดยไม่รู้ว่าคืออะไร
- ทุกการเปลี่ยน schema ต้องผ่าน migration ห้ามแก้ฐานข้อมูลด้วยมือ และห้ามแก้ไฟล์ migration ที่ commit ไปแล้ว ให้เพิ่มไฟล์ใหม่
- ตารางใหม่หรือคอลัมน์ลับใหม่ ต้องตัดสินใจเรื่องหน้า SQL ทุกครั้ง ดูข้อ 20

## 12. Serde

- struct สำหรับ JSON ขาเข้าใส่ `#[serde(deny_unknown_fields)]` เพื่อให้พิมพ์ชื่อฟิลด์ผิดแล้วฟ้องทันที
- **ห้าม derive `Serialize` ให้ struct ที่มี `password_hash` หรือ token** ใช้ struct สำหรับ response แยกต่างหาก
- ทุก DTO ใช้ `#[serde(rename_all = "camelCase")]` ตามที่ตกลงกับ frontend แล้ว
- id ที่ส่งออก API เป็น `uuid` เสมอ ห้ามส่ง id int ภายใน (ดูข้อ 20)

## 13. Log

- ใช้ `tracing` ไม่ใช้ `println!` หรือ `eprintln!`
- `error!` สำหรับสิ่งที่ต้องมีคนมาดู, `warn!` สำหรับสิ่งผิดปกติที่ระบบรับมือได้แล้ว, `info!` สำหรับเหตุการณ์สำคัญทางธุรกิจ (login, สร้างผู้ใช้), `debug!` สำหรับรายละเอียดตอนพัฒนา
- ใช้ field แบบมีโครงสร้าง เช่น `info!(user_id = %id, "login succeeded")` ไม่ใช่การต่อ string
- `#[instrument]` ต้องระบุ `skip` สำหรับพารามิเตอร์ที่มีความลับเสมอ
- **ห้าม log** รหัสผ่าน, session token, ค่า cookie, ข้อมูลผู้ป่วย (ทั้ง plaintext และ ciphertext) และ key เข้ารหัส ไม่ว่ากรณีใด รวมถึงตอนเกิด error
- request id: ยังไม่ได้ทำ (feature `request-id` ของ tower-http เปิดไว้ใน `Cargo.toml` แล้ว) เป้าหมายคือให้ทุก log ของ
  request มี request id ติดไปด้วย ถ้าจะทำให้ใส่ที่ `app.rs` ร่วมกับ `TraceLayer`

## 14. เวลา

- เลือก crate เดียวทั้งโปรเจกต์ (`chrono`) แล้วใช้ `DateTime<Utc>` ทุกที่
- ห้ามใช้ `Local::now()` ในโค้ดฝั่ง backend
- การแปลงเป็นเวลาไทยทำที่ชั้นแสดงผลเท่านั้น
- ฟังก์ชันที่ตรรกะขึ้นกับเวลา ให้รับเวลาเป็นพารามิเตอร์ จะเทสง่ายกว่าเรียก `Utc::now()` ข้างใน
  - `Utc::now()` เรียกได้ที่ handler หรือ extractor แล้วส่งลงไป
  - `service.rs` และ `repository.rs` ไม่เรียกเอง (ดูหัวไฟล์ `auth/service.rs`)
- เมื่อตรรกะต้องใช้ "วัน" ของผู้ใช้ (อายุ, วันเกิด, วันนัด) ให้คำนวณวันไทยที่ขอบระบบแล้วส่ง `NaiveDate` ลงไป
  เช่น `today_in_thailand()` ใน `patient/handlers.rs` อย่าตัดวันจาก `DateTime<Utc>` ตรง ๆ เพราะช่วง 00:00–07:00 จะได้วันผิด
  - ข้อยกเว้น: ถ้าแค่ตรวจว่าวันที่ที่ผู้ใช้กรอก "ไม่เกินวันนี้ตามเวลาไทย" อ่านวันนี้จากนาฬิกา DB ผ่าน repository ได้
    (`stock/repository/mod.rs::thai_today` ที่ใบรับใช้ ใบเบิกจะใช้ตัวเดียวกัน) เพราะเทสเทียบกับนาฬิกา DB เดียวกัน
    และไม่ต้องเพิ่ม crate timezone ตรรกะเวลาอื่นยังรับเวลาเป็นพารามิเตอร์ตามข้อบน

## 15. Config และค่าคงที่

- อ่าน environment variable ที่เดียวใน `config.rs` ตอนเริ่มระบบ แล้วส่งค่าที่ parse แล้วไปใช้
- ถ้าค่าที่จำเป็นหายหรือผิดรูปแบบ ให้ล้มตั้งแต่ตอนเริ่ม ไม่ใช่ตอนมี request เข้ามา
- ห้าม `std::env::var` กระจายอยู่กลางโค้ด
- ตัวเลขที่มีความหมาย (อายุ session, จำนวนครั้งที่ผิดได้, ขนาด body, timeout) ต้องเป็นค่าคงที่ที่มีชื่อหรืออยู่ใน config ไม่ใช่ตัวเลขลอย ๆ ในโค้ด
  - ตัวอย่าง: `MAX_BODY_BYTES` และ `BODY_READ_TIMEOUT` ใน `app.rs`
  - ถ้าค่ามาจากการคำนวณ (เช่น ทำไมต้อง 3 วินาที) ให้เขียนเหตุผลเป็นคอมเมนต์เหนือค่าคงที่

## 16. Dependency

- ถามก่อนเพิ่ม crate ใหม่ทุกครั้ง การเปิด feature เพิ่มของ crate เดิมไม่นับเป็น dependency ใหม่ แต่ให้คอมเมนต์ใน `Cargo.toml` ว่าเปิดไว้ทำอะไร
- เลือก crate ที่มีคนใช้มากและยังอัปเดตอยู่ ถ้าเขียนเองได้ใน 30 บรรทัดและไม่ใช่เรื่องความปลอดภัย ให้เขียนเอง
- เรื่องที่เกี่ยวกับการเข้ารหัสหรือ hash **ห้ามเขียนเอง** ใช้ crate ที่เป็นมาตรฐานเท่านั้น
- ตรึงเวอร์ชันใน `Cargo.lock` และ commit ขึ้น git
- TLS ใช้ rustls ตัวเดียวทั้งโปรเจกต์ (provider ring เดียวกับ sqlx) อย่าดึง OpenSSL หรือ provider ตัวที่สองเข้ามา (ดูคอมเมนต์ `reqwest` ใน `Cargo.toml`)

## 17. เทส

- unit test อยู่ใน `#[cfg(test)] mod tests` ท้ายไฟล์เดียวกัน สำหรับตรรกะล้วน ๆ
- integration test อยู่ใน `backend/tests/` ยิงผ่าน router จริง ใช้ `#[sqlx::test]` เพื่อให้ได้ฐานข้อมูลสะอาดต่อเทส ส่วนช่วยร่วมอยู่ใน `tests/common/`
- ชื่อเทสบอกพฤติกรรมที่คาดหวัง เช่น `login_with_wrong_password_returns_same_error_as_unknown_user`
- ห้าม `sleep` ในเทสเพื่อรอเวลา ให้ฉีดเวลาเข้าไปเป็นพารามิเตอร์แทน ถ้าเทสต้องตรวจค่าที่ขึ้นกับเวลา (เช่น `Retry-After`) ให้ตรวจเป็นช่วง ไม่ใช่ค่าเดียว
- ทุก bug ที่เจอ ให้เขียนเทสที่ทำให้มันล้มก่อน แล้วค่อยแก้
- endpoint ใหม่ที่ต้องใช้สิทธิ์ ต้องมีเทสอย่างน้อยหนึ่งตัวที่ผู้ใช้ไม่มีสิทธิ์ถูกปฏิเสธ (ดู `tests/permissions.rs`)

## 18. เครื่องมือ

- `cargo fmt` ก่อน commit เสมอ ไม่ตั้งค่า rustfmt เอง ใช้ค่ามาตรฐาน
- `cargo clippy --all-targets -- -D warnings` ต้องผ่าน
- `#[allow(...)]` ใส่ได้เฉพาะเมื่อมีคอมเมนต์อธิบายเหตุผลบรรทัดถัดไป และให้ใส่แคบที่สุดเท่าที่ทำได้ ห้ามใส่ระดับไฟล์หรือ crate (ตอนนี้ทั้งโปรเจกต์ยังไม่มีสักที่)

## 19. สิ่งที่ยังไม่ต้องทำในโปรเจกต์นี้

เพื่อไม่ให้โปรเจกต์งานอดิเรกกลายเป็นภาระ

- ไม่ต้องทำ trait abstraction ของ repository เพื่อรองรับฐานข้อมูลอื่น
- ไม่ต้องเขียน macro ของตัวเอง
- ไม่ต้องทำ generic ที่มีพารามิเตอร์หลายตัวเพื่อความยืดหยุ่นที่ยังไม่มีใครขอ
- ไม่ต้องทำ workspace หลาย crate จนกว่าเวลาคอมไพล์จะเป็นปัญหาจริง
- ไม่ต้องปรับแต่งประสิทธิภาพก่อนวัด ระบบนี้มีผู้ใช้ไม่กี่คน ความอ่านง่ายสำคัญกว่าความเร็วเสมอ
  (ข้อยกเว้นคือเพดานที่กันการโจมตี เช่น จำนวน connection, ขนาด body, งาน argon2 พร้อมกัน ซึ่งเป็นเรื่องความปลอดภัย ไม่ใช่ประสิทธิภาพ)

## 20. ข้อมูลผู้ป่วยและความลับ

สรุปจาก CLAUDE.md หัวข้อ "ขอบเขตข้อมูล" ถ้าขัดกันให้ยึด CLAUDE.md

- คอลัมน์ที่ data dict ระบุ `encrypt = yes` ต้องเข้ารหัสด้วย `crypto.rs` ก่อนลง DB เสมอ (เก็บเป็น `bytea`)
  - ห้ามเขียน plaintext ลง DB
  - ห้ามใช้ argon2 กับคอลัมน์เหล่านี้
- ค้นหาคอลัมน์เข้ารหัสด้วย blind index (`*_idx`) เท่านั้น ห้ามถอดรหัสทั้งตารางมา filter ใน Rust
- คอลัมน์เข้ารหัสใหม่ต้องเพิ่มใน `domain/patient_crypto.rs` ไม่งั้นหน้า SQL จะถอดรหัสไม่ได้
- ตารางใหม่ต้องตัดสินใจว่าหน้า SQL เห็นไหม
  - ถ้าให้เห็น ให้เพิ่มใน `READABLE_TABLES` (`sql_console/setup.rs`)
  - คอลัมน์ลับ (hash, token, รหัส) ในตารางที่อ่านได้ ต้องเพิ่มใน `HIDDEN_COLUMNS` ไม่งั้นจะถูก grant ให้อัตโนมัติ
- API ส่งข้อมูลที่ถอดรหัสแล้วเฉพาะ endpoint ที่จำเป็น และใช้ `uuid` แทน id int ภายในเสมอ
  - โมดูลที่ไม่ต้องรู้ตัวตนคนไข้คืนแค่ uuid เช่น `lab_visit/`
- ห้ามใส่ข้อมูลผู้ป่วย (plaintext หรือ ciphertext) หรือ key (`DATA_ENCRYPTION_KEY`, `BLIND_INDEX_KEY`) ใน log, `audit_log.metadata` และ error message
  - audit ของแถวผู้ป่วยไม่มีชื่อรายการ
- ห้ามเก็บเลขบัตรประชาชน
