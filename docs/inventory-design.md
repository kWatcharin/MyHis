# ดีไซน์ระบบบริหารจัดการคลัง (Inventory) — my-his

> **สถานะ: ร่างสำหรับอ่านและตกลงขอบเขต ยังไม่มีโค้ด** ชื่อตาราง/สิทธิ์ในเอกสารนี้เป็นข้อเสนอ ยังไม่ผูกมัด
> งานนี้เริ่มหลัง Milestone 1 (auth) เสร็จ เขียนขึ้นเพราะเจ้าของโปรเจกต์ไม่เคยทำระบบคลังมาก่อน
> จึงอธิบายแนวคิดควบคู่กับดีไซน์

## 1. ขอบเขตที่ตกลงแล้ว

| เรื่อง | คำตอบ | ผลต่อการออกแบบ |
|---|---|---|
| ประเภทของ | ผสมหลายประเภท (ยา, เวชภัณฑ์สิ้นเปลือง, วัสดุแล็บ) | ธง `track_lot` / `track_expiry` เป็นของ *แต่ละรายการ* ไม่ใช่ทั้งระบบ |
| ผูกผู้ป่วย | ผูกด้วย `patient_id` เท่านั้น | แบบเดียวกับ `lab_visit`: เก็บ FK ภายใน, API คืนแค่ `uuid`, ไม่คัดลอกชื่อ/HN ลงตารางคลัง |
| ราคา/มูลค่า | ยังไม่ติดตาม | ไม่มีคอลัมน์ราคาในรอบแรก เพิ่มทีหลังได้โดยไม่กระทบ ledger |
| ขนาดการใช้งาน | ที่เก็บเดียว ผู้ใช้ไม่กี่คน | ตัดการโอนย้าย, ขั้นอนุมัติ, และตารางที่เก็บออกจากรอบแรก |

**ยังไม่ทำในรอบแรก** (ออกแบบให้เติมทีหลังได้โดยไม่ต้องรื้อ): หลายที่เก็บและการโอนย้าย, ต้นทุน/มูลค่าคงคลัง,
ใบสั่งซื้อ, ขั้นอนุมัติ, สแกนบาร์โค้ด, แจ้งเตือนนอกระบบ (LINE/อีเมล)

## 2. แกนความคิด (จำ 3 ข้อนี้ก่อน)

1. **คลังคือสมุดบัญชีการเคลื่อนไหว ไม่ใช่ตารางตัวเลขคงเหลือ**
   ทุกครั้งที่ของเข้า ออก หรือปรับยอด ให้ *เพิ่มแถวใหม่* ใน ledger (`stock_movement`) ยอดคงเหลือคือผลรวมของแถวเหล่านั้น
   ไม่แก้เลขทับ ไม่ลบแถว ถ้าผิดให้ลงรายการ "กลับรายการ" เพิ่ม — ไล่ย้อนได้เสมอว่ายอดมาจากไหน
2. **ของชิ้นเดียวกันแยกด้วยล็อตและวันหมดอายุ** ต้องรู้ว่าล็อตไหนหมดก่อน และเบิกล็อตที่หมดก่อนออกก่อน (FEFO)
3. **ทุกการเคลื่อนไหวต้องมีเหตุผลและคนทำ** ใช้ `created_by` และ `audit_log` แนวเดียวกับโมดูลอื่น

## 3. คำศัพท์

| คำ | ความหมาย | ตัวอย่าง |
|---|---|---|
| Item (รายการ) | สิ่งที่เก็บ — master data | พาราเซตามอล 500 mg, ถุงมือ size M, หลอดเก็บเลือด |
| Category (หมวด) | จัดกลุ่มรายการ และกำหนดค่าเริ่มต้นของธง | ยา, เวชภัณฑ์สิ้นเปลือง, วัสดุแล็บ |
| Unit (หน่วย) | หน่วยนับ มี **หน่วยฐาน** = หน่วยเล็กสุดที่เบิกจริง | 1 กล่อง = 10 แผง = 100 เม็ด → เก็บเป็น "เม็ด" |
| Lot (ล็อต) | ชุดผลิตเดียวกัน มี lot no. และวันหมดอายุ | lot A123 หมด 2027-03 |
| Movement | 1 แถวใน ledger: เข้า (+) หรือออก (−) | รับเข้า 100 เม็ด / เบิก 30 เม็ด |
| On-hand (คงเหลือ) | ผลรวม movement ต่อ item × lot | |
| Reorder point | ระดับที่ควรสั่งเพิ่ม | |

## 4. Flow หลัก

```
รับเข้า ──► เก็บ ──► เบิกจ่าย/ใช้ ──► (เหลือน้อย → ไปสั่งของเพิ่ม แล้ววนกลับมารับเข้า)
              │
              ├──► ตรวจนับ ──► ปรับยอด (ส่วนต่าง)
              └──► หมดอายุ/เสียหาย ──► ตัดจำหน่าย
```

| ขั้น | ทำอะไร | ผลต่อ ledger | ต้องบันทึก |
|---|---|---|---|
| รับเข้า | ของมาถึง ตรวจจำนวน/ล็อต/หมดอายุ/สภาพ | +จำนวน ต่อล็อต | วันที่รับ, แหล่งที่มา, เลขเอกสาร, lot, วันหมดอายุ, ผู้รับ |
| เบิกจ่าย | ใช้/จ่ายให้หน่วยงานหรือผู้ป่วย ระบบเลือกล็อตหมดอายุก่อน (FEFO) | −จำนวน ต่อล็อต | เหตุผล/ปลายทาง, `patient_id` (ถ้าผูก), ผู้เบิก |
| ตรวจนับ | นับจริงเทียบกับในระบบ (รายเดือนหรือสิ้นปีงบ) | ยังไม่เปลี่ยนจนกว่ายืนยัน | จำนวนนับจริง vs ในระบบ |
| ปรับยอด | ลงส่วนต่างจากการนับ ของหาย ของเสียหาย | ±ส่วนต่าง | **เหตุผล (บังคับ)**, ผู้ทำ |
| ตัดจำหน่าย | ของหมดอายุ/เสื่อมสภาพ | −จำนวน | เหตุผล เช่น หมดอายุ/ชำรุด |

"ยอดยกมา" ตอนเริ่มใช้ระบบก็คือ movement ชนิด `opening` — ไม่มีทางลัดที่ตั้งยอดตรง ๆ

## 5. กฎที่ต้องบังคับ

- **ห้ามคงเหลือติดลบ** — ตรวจในชั้น service ตอนเบิก และกันซ้ำด้วย `CHECK (qty_on_hand >= 0)` ที่ DB
- **เบิกพร้อมกันสองคำขอต้องไม่ทำให้ยอดเพี้ยน** — เบิกใน transaction เดียว ล็อกแถว balance ของล็อตนั้นด้วย
  `SELECT … FOR UPDATE` ก่อนอ่านแล้วค่อยหัก (race condition คลาสสิกของระบบคลัง)
- **ledger เป็น append-only** — ไม่มี `UPDATE` และไม่มี soft delete ของ movement; แก้ผิดด้วย movement กลับรายการที่อ้างแถวเดิม
  (ต่างจาก master ที่ใช้ soft delete ตามกฎโปรเจกต์ — เหตุผลคือ ledger ต้องเป็นหลักฐาน ไม่ใช่ข้อมูลตั้งค่า)
- **จำนวนใช้ `integer` หรือ `numeric` ห้าม float** และเก็บเป็น *หน่วยฐาน* เสมอ แปลงจากกล่อง/แผงตอนกรอกฟอร์มเท่านั้น
- **ห้ามเบิกของหมดอายุ** — service ข้ามล็อตที่หมดอายุแล้ว และรายงานเตือนของใกล้หมดอายุ (เช่น 90 วัน ปรับค่าได้)
- **เวลาเก็บเป็น UTC (`timestamptz`)** แปลงเป็นเวลาไทยตอนแสดงผลเท่านั้น (เวรดึกคร่อมเที่ยงคืน วันที่เบิกต้องไม่เพี้ยน)
- **ทุก movement อ้างเอกสารต้นทาง** (`doc_type` + `doc_id`) เพื่อไล่กลับจากยอดไปหาเอกสารได้

### การเลือกล็อต (FEFO)

ตอนเบิก service เรียงล็อตที่ยัง `qty_on_hand > 0` และยังไม่หมดอายุ ตาม `expiry_date` น้อยไปมาก (ล็อตที่ไม่มีวันหมดอายุไว้ท้าย)
แล้วหักไล่ทีละล็อตจนครบจำนวน — ถ้ารวมทุกล็อตยังไม่พอ ปฏิเสธทั้งคำขอ (ไม่หักบางส่วน)
รายการที่ไม่ติดตามล็อต (`track_lot = false`) ใช้ "ล็อตเดียวไม่ระบุ" ที่ระบบสร้างให้ ledger จึงหน้าตาเดียวกันทุกชนิด ไม่ต้องแตกสองทาง

## 6. โมเดลข้อมูล (ร่าง)

รูปแบบเหมือนตารางอื่นของโปรเจกต์: `id` int identity + `uuid` v7 (ส่งออก API เฉพาะ uuid), `created_by/at`, `updated_by/at`
master ใช้ soft delete (`deleted_by/at`) ส่วนตาราง ledger ไม่มี soft delete

**Master (หน้าตั้งค่า โครงเดียวกับ `disease/`):**

| ตาราง | คอลัมน์สำคัญ |
|---|---|
| `item_category` | ชื่อ, ค่าเริ่มต้นของ `track_lot` / `track_expiry` / `patient_linkable` |
| `unit` | ชื่อหน่วย |
| `item` | ชื่อ, `category_id`, `base_unit_id`, `track_lot`, `track_expiry`, `patient_linkable`, `reorder_point`, `is_active` |
| `item_unit_conversion` | `item_id`, `unit_id`, `factor` (กี่หน่วยฐานต่อ 1 หน่วยนี้) |

**ธุรกรรม:**

| ตาราง | หน้าที่ |
|---|---|
| `stock_lot` | `item_id`, `lot_no`, `expiry_date`, `received_date` — unique (`item_id`, `lot_no`) |
| `stock_balance` | `lot_id`, `qty_on_hand` (หน่วยฐาน) + `CHECK (qty_on_hand >= 0)` — อัปเดตใน transaction เดียวกับ movement |
| `stock_movement` | **ledger**: `lot_id`, `qty_delta` (±), `movement_type`, `reason`, `doc_type`, `doc_id`, `reverses_id` (nullable), `created_by/at` |
| `stock_receipt` + `_line` | หัวเอกสารรับเข้า (วันที่, แหล่งที่มา, เลขเอกสาร) + รายการ (item, lot, วันหมดอายุ, จำนวน) |
| `stock_issue` + `_line` | หัวเอกสารเบิก (วันที่, เหตุผล/ปลายทาง) + รายการ (item, จำนวน, `patient_id` nullable) |
| `stock_count` + `_line` | รอบนับ + จำนวนนับจริง/จำนวนในระบบ ต่อล็อต |
| `stock_adjustment` | เอกสารปรับยอด/ตัดจำหน่าย มี reason บังคับ |

`stock_balance` เก็บแยกเพื่ออ่านเร็วและเป็นจุดที่ใช้ล็อกกันเบิกซ้อน — ต้องตรวจเสมอว่า **Σ `qty_delta` ของ ledger = `qty_on_hand`**
(เป็นเทสสำคัญที่สุดของโมดูลนี้) ถ้าข้อมูลน้อยมากอาจเริ่มด้วยการ SUM จาก ledger ตรง ๆ ก่อนก็ได้ แต่จะไม่มีแถวให้ล็อต และต้องกัน
race ด้วยวิธีอื่น จึงแนะนำให้มี `stock_balance` ตั้งแต่ต้น

เลขเอกสาร (รับ/เบิก/ปรับ) ควรรันต่อเนื่องแยกตามปีงบประมาณ (`budget_year` มีอยู่แล้ว) — ยังต้องตัดสินใจรูปแบบ

## 7. เข้ากับกฎของโปรเจกต์อย่างไร

- **โครงโมดูล:** receive / issue / count / adjust ล้วนต้องลง ledger เหมือนกัน ตรรกะ "post movement" (เช็คติดลบ, เลือกล็อต FEFO,
  อัปเดต balance) จึงอยู่ที่เดียว ตามกฎ "โมดูลฟีเจอร์ไม่เรียกกันเอง" มีสองทางที่ใช้ได้:
  - โมดูล `stock/` เดียว แยกไฟล์ย่อยตามเอกสาร (แบบ `users/service/pages.rs`, `users.rs`) — **แนะนำ** เพราะทุกเอกสารร่วม ledger เดียวกัน
  - หรือย้ายตรรกะ post movement ลง `domain/` แล้วแยกโมดูลต่อเอกสาร
  - master (`item_category`, `unit`, `item`) แยกโมดูลเหมือน `disease/`, `lab/` ได้ตามปกติ
- **สิทธิ์:** รูปแบบ `resource.action` ตรวจแยกกันทุกตัว เช่น `stock_item.*` (master), `stock_receipt.*`, `stock_issue.*`,
  `stock_count.*`, `stock_adjust.*` — **ปรับยอด/ตัดจำหน่ายเป็นสิทธิ์แยก** เพราะเสี่ยงที่สุด และไม่ implies สิทธิ์เบิก
- **ผูกผู้ป่วย:** `stock_issue_line.patient_id` เป็น FK ไป `patient.id` ภายในเท่านั้น
  - API ส่ง `uuid` ของคนไข้ ไม่ส่ง id int
  - หน้าที่ต้องแสดงชื่อ/HN join กับ `GET /patients` ฝั่งหน้าเว็บ จึงต้องมี `patient.view` ด้วย (วิธีเดียวกับ `lab_visit/service.rs`)
  - `audit_log.metadata` และ error message ของการเบิก **ห้ามมีชื่อ/HN** ของผู้ป่วย
  - ผูกได้เฉพาะรายการที่ติดธง `patient_linkable` (เช่นยา)
- **audit:** ทุกเอกสารเขียน `audit_log` เองเหมือนโมดูลอื่น (ใครรับ/เบิก/ปรับ) แถวที่เกี่ยวกับผู้ป่วยไม่มีชื่อรายการตามแนวเดิม
- **ตารางใหม่ + หน้า SQL:** ตัดสินใจทุกตารางว่าเพิ่มใน `READABLE_TABLES` (`backend/src/sql_console/setup.rs`) ไหม — ข้อมูลคลังไม่ใช่
  ข้อมูลลับ น่าจะเปิดอ่านได้ ยกเว้น `stock_issue_line.patient_id` ซึ่งต้องพิจารณาคู่กับตาราง `patient` ที่เข้ารหัส
- **เอกสารที่ต้องอัปเดตตอนลงมือ:** `docs/my-his-data-dict.xlsx` (ทุกตาราง), `docs/auth-design.md` (สิทธิ์ใหม่), `CLAUDE.md` (โครงสร้างโมดูล)
- **เวลา:** `timestamptz` UTC; **soft delete:** เฉพาะ master

## 8. รายงานขั้นต่ำ

| รายงาน | ตอบคำถาม |
|---|---|
| Stock card รายรายการ | เข้า/ออก/คงเหลือสะสมของรายการนี้เป็นอย่างไร |
| คงเหลือปัจจุบัน | มีของอะไรอยู่เท่าไร แยกตามล็อตและวันหมดอายุ |
| ใกล้หมดอายุ | ล็อตไหนจะหมดภายใน N วัน |
| ต่ำกว่า reorder point | ต้องสั่งอะไรเพิ่ม |
| ยอดใช้รายเดือน | ใช้ไปเท่าไร (ใช้คำนวณ reorder point) |
| ส่วนต่างตรวจนับ | นับจริงต่างจากระบบตรงไหน |

**สูตร** (ตามกฎโปรเจกต์ที่ต้องแสดงสูตรและหน่วยควบคู่ผลลัพธ์ — หน้าจอต้องแสดงสูตรนี้ให้ตรวจด้วยตาได้):

- Reorder point (หน่วยฐาน) = อัตราใช้เฉลี่ย (หน่วยฐาน/วัน) × lead time (วัน) + safety stock (หน่วยฐาน)
- คงเหลือ (หน่วยฐาน) = Σ `qty_delta` ของ movement ทั้งหมดของล็อตนั้น
- ส่วนต่างตรวจนับ (หน่วยฐาน) = จำนวนนับจริง − จำนวนในระบบ

ในรอบแรกอาจให้ผู้ใช้กรอก `reorder_point` เองต่อรายการก่อน แล้วค่อยทำตัวช่วยคำนวณทีหลัง

## 9. ลำดับการทำที่แนะนำ

1. **Master:** หมวด, หน่วย, รายการ (+ การแปลงหน่วย) และยอดยกมา — ได้หน้าตั้งค่าที่ซ้ำแนวเดิม เสี่ยงต่ำ
2. **รับเข้า + เบิกจ่าย + ledger + stock card** — หัวใจของระบบ ทำให้ถูกก่อนอย่างอื่น
3. **ตรวจนับ + ปรับยอด/ตัดจำหน่าย**
4. **รายงานเตือน:** ใกล้หมดอายุ, ต่ำกว่า reorder point
5. *(ทีหลังถ้าจำเป็น)* หลายที่เก็บ + โอนย้าย, ต้นทุน, ใบสั่งซื้อ, ผู้อนุมัติ

## 10. การทดสอบ

เทสระดับ API ใน `backend/tests/` ผ่าน router จริง ด้วย `#[sqlx::test]` ตามแนวของโปรเจกต์ กรณีที่ต้องมี

- เบิกเกินคงเหลือถูกปฏิเสธ และไม่หักบางส่วน
- เบิกพร้อมกันสองคำขอบนของชิ้นสุดท้าย → สำเร็จหนึ่ง ปฏิเสธหนึ่ง ไม่ติดลบ
- เบิกแล้วได้ล็อตที่หมดอายุก่อน (FEFO) และข้ามล็อตที่หมดอายุแล้ว
- กลับรายการแล้วยอดคืน และ movement เดิมไม่ถูกแก้
- **Σ ledger = `stock_balance` เสมอ** หลังทุกชุดของธุรกรรม
- แปลงหน่วย: รับเป็นกล่อง เบิกเป็นเม็ด ยอดถูกต้องในหน่วยฐาน
- ผู้ไม่มีสิทธิ์ถูกปฏิเสธ แยกทีละ action (ดู/เบิก/ปรับยอด)
- เบิกผูกผู้ป่วย: API ไม่คืน id int และ `audit_log` ไม่มีชื่อ/HN

## 11. คำถามที่ยังเปิดอยู่

1. ต้องการ "แหล่งที่มา" (ผู้ขาย/ผู้บริจาค) เป็น master ไหม หรือพิมพ์ข้อความอิสระตอนรับเข้า
2. เหตุผลการเบิก/ปรับยอด ใช้รายการตายตัว (master) หรือข้อความอิสระ — แนะนำรายการตายตัวสำหรับ reason ของการปรับยอด เพื่อสรุปรายงานได้
3. เกณฑ์ "ใกล้หมดอายุ" ค่าเดียวทั้งระบบ หรือแยกตามหมวด
4. รูปแบบเลขเอกสารและรอบรันเลขต่อปีงบประมาณ
5. รายการที่ติดธง `patient_linkable` ต้องบังคับระบุผู้ป่วยทุกครั้งที่เบิก หรือเลือกได้
6. ผู้ใช้กลุ่มไหนควรมีสิทธิ์ปรับยอด (ใช้ role ที่มีอยู่หรือสร้างใหม่)
